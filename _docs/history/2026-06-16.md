## gen_dataset_v4: 바닥 텍스처 8종 랜덤화 + 예시 10장 검증 (3d-expert)

### 목적
합성 바닥이 1종(그레이팅 base_m)으로 과적합되는 문제 대응. 바닥 8종 + UV scale/tint
per-frame 랜덤화를 gen 파이프라인에 적용하고, 예시 10장으로 다양성·자연접지·라벨 무영향
검증. 풀 5000 재생성은 OK 후 별도(이번엔 10장까지만).

### 핵심: 그레이팅 함정 → fresh plane drop
직전 floor compare(memory 36)에서 확인된 함정: `Base_base_m_0`(base_m)는 평면이 아니라
도랑 그레이팅 지오메트리 → 실사 텍스처가 슬랫에 쪼개져 회색 줄무늬. 단색은 반영되나
실사 albedo는 안 됨. 해법 = base_m 재텍스처가 아니라 **팔레트 centroid 아래 z=0 평면을
새로 깔고 그 평면에 텍스처**. 그레이팅/펜스/차선마크는 hide.

### ★ 핵심 설계: FLOOR_PLANE_Z=-6mm (raycast 게이트 보존)
모든 물체(팔레트/박스/distractor)는 snap_object_to_ground로 바닥 z=0에 접지.
raycast 가시성 게이트의 silhouette 점은 팔레트 바닥 코너(z≈0)에 있음 → 평면을 정확히
z=0에 두면 평면이 그 점들을 가려 occlusion 오판 위험. **평면을 z=-6mm(서브픽셀)로 살짝
내려** 깔면 시각적 접지/그림자는 동일하되 on-ground 점으로 향하는 ray가 평면보다 먼저
팔레트에 도달 → raycast 게이트 무영향. distractor도 각자 z=0 접지라 평면이 높이를
바꾸지 않음(서로 상대 높이 보존).

### 핵심 교훈
- "0123 image-quadrant" 사인 검사(corner가 quad centroid 기준 TL/TR/BR/BL인지)는 flat 팔레트에
  **부적합(54/120 false-violation)**. oblique 뷰에서 top/bot edge가 기울어 corner가 축정렬
  centroid 반대편에 앉음. 올바른 판정 = simple-quad + 0top + 0left(자기 프레임 기준).
  → flat 물체 라벨판정은 단일임계 oracle 금지, conn_x+front_near+육안(memory 재확인).
- raycast 게이트가 throughput 최대 병목(86%). pass rate 낮은 건 게이트가 점유/grazing을 정상
  배제하는 것. 풀 시간단축 원하면 box occlusion_target/distractor 밀도 완화 검토(robustness trade-off).
- nohup wrapper "completed exit0" 알림은 자식 Blender 종료 아님 → tasklist로 실종료 확인 후 검증.

### 미해결 / 사용자 결정 필요
- 풀 5000 생성 GO 여부(예상 ~21.6시간 1회 실행). overlay_every=100 권장.
- raycast 86% reject 수용 여부: 시간 vs 데이터셋 난이도 trade-off. 현 설정은 점유 팔레트를

## look_at jitter — 화면 중앙쏠림 제거 (cam_test10b)

### 배경
직전 cam_test10에서 centroid가 항상 화면 정중앙(320,240)인 게 `sample_camera_elev`의 look_at=centroid 고정 조준 탓이라 확인됨. 이번 작업으로 look_at에 랜덤 jitter를 줘 팔레트가 화면 중앙~구석 다양한 위치에 등장하게 함. 나머지 설정(elev 15~65, azim 360, scene 1/3, 머티리얼, 비율랜덤 40%, HDRI 7종, raycast 0.30, 게이트) 전부 미변경.

### 변경 (scripts/data_prep/blender/gen_dataset_v4.py)
- 상수 추가(RATIO_RANGE 아래): `LOOKAT_JITTER=True`, `LOOKAT_JITTER_NORM_LO/HI=0.25/0.75`, `REQUIRE_ALL_CORNERS_IN_FRAME=True`.
- `sample_camera_elev`: cam_pos 결정 후 look_at를 **카메라 image-plane에서 평행이동**.
  - `R_w2c0,_=build_view_matrix(cam_pos, centroid)`; `right=R_w2c0[0]`, `cam_up=-R_w2c0[1]`.
  - 목표 정규화 화면위치 `nx,ny~U(0.25,0.75)`; 픽셀오프셋 `du=(nx-.5)*W,dv=(ny-.5)*H`; world이동 `dx=du*d/fx,dy=dv*d/fy`(d=cam→centroid).
  - `look_at = centroid - right*dx - cam_up*dy`. look_at만 옮기면 annotation 파이프라인(build_view_matrix 재호출) 그대로 off-center 투영 → compute_perm_v4/visibility/conn_cross 무변경.
- gate 추가(reason 체인): 8코너 전부 in-frame 아니면 `area/vis`로 reject(truncation 배제). `REQUIRE_ALL_CORNERS_IN_FRAME` 토글. (기존 visible_min_fraction=0.60은 truncation 통과시킴 → test용으로 strict.)

### 결과 (seed9300, 10장, data/pallet/_cam_test10b/train/)
- 화면위치 분산: x_norm 0.33~0.65(std .086), y_norm 0.28~0.75(std .164), dist-from-center mean 0.182(이전 0.0). 사분면 RU5/RD3/LU2.
- 10/10 all-8-in-frame, connX=0, front_is_camera_near=True. overlay+full image 육안: cuboid가 팔레트 모서리 정확 정렬, 머티리얼 정상.
- pass-rate 37%→16.7%(60 cand: area/vis25 raycast14 grazing11 PASS10), 5.5s/frame. truncation 게이트가 area/vis로 흡수.

### 풀 5000 GO 전 결정사항
- jitter 채택(0.25~0.75)로 중앙쏠림 해소. pass-rate ~17%(이전 37%) → 동일 5000장에 약 2.2x 후보 필요(시간 비례 증가). 허용 가능하면 GO.
- 더 강한 off-center 원하면 NORM_LO/HI 넓히되 pass-rate 추가하락. truncation robustness 학습 원하면 `REQUIRE_ALL_CORNERS_IN_FRAME=False`(현재 test용 True).

## run_dataset_v4: 폴더 분할(folder-split) 저장 구조 추가 (3d-expert)

풀 5000장 생성 직전, 한 폴더에 다 넣지 않고 **폴더당 200장씩 독립 DOPE 데이터셋**으로 분할 저장하도록 변경.

### 변경 파일
- `scripts/data_prep/blender/gen_dataset_v4.py`
  - `parse_args()`: `--flat_out` 플래그 추가 (action="store_true"). out_dir 밑에 `<split>/` 서브디렉토리를 만들지 않고 out_dir 자체를 데이터셋 루트로 사용.
  - `main()` split_dir 계산: `split_dir = out_root if args.flat_out else os.path.join(out_root, args.split)`. 나머지 엔진/게이트/라벨 로직은 일절 변경 없음.
- `scripts/data_prep/blender/run_dataset_v4.sh` (전면 재작성)
  - 새 인자 `--per_folder`(기본 200). `--batch_size`(fresh Blender chunk, per_folder로 clamp).
  - 폴더 네이밍: `train_batch_%03d` / `val_batch_%03d` (zero-pad 3자리). out_dir 바로 밑에 생성.
  - `run_split()`: total을 per_folder 단위로 ceil 분할 → 폴더 개수 계산. 마지막 폴더는 나머지(<per_folder)만 채움(PER_FOLDER 일시 축소).
  - `fill_folder()`: 폴더당 PER_FOLDER까지 chunk(=batch_size) 단위로 fresh Blender 호출. `--flat_out` + `--out_dir <out>/<folder>` 전달. frame index는 폴더 내 0부터 ({i:06d}).
  - **frame index 정책**: 폴더별 0부터 시작(전역 연속 아님). 각 batch 폴더가 독립 DOPE 데이터셋 → 로더가 폴더 하나만 가리켜도 동작.
  - **resume**: 폴더별 images/*.png 카운트. count>=per_folder 폴더는 SKIP, 부분 폴더는 현재 count부터 이어감(start_idx=count). seed = seed_base + folder*10000 + done_count (폴더/재개 chunk마다 달라 동일 프레임 반복 방지).
  - 메모리 가드: chunk(=폴더 또는 batch_size 프레임)마다 fresh Blender 프로세스 유지(기존과 동일).

### 소량 검증 (data/pallet/_split_test, 검증 후 삭제됨)
- batch_size=6, per_folder=6, n_train=14, n_val=6, seed=9000
- 결과: train_batch_000(6) / train_batch_001(6) / train_batch_002(2) / val_batch_000(6) — 정확히 6장 단위 분할, 마지막 폴더 2장.
- 각 폴더 images/json 쌍 일치(6/6, 2/2, 6/6), frame index 폴더 내 000000부터, _stats(chunk_000000.json)·overlay(every100 → 000000만) 폴더별 생성.
- resume: train_batch_001에서 000004/000005 삭제(4장) 후 재실행 → 000/002/val SKIP, 001만 index4부터 이어 6/6 복원. 라벨 정상(camera_dynamic_0123_v4, dynamic perm, dims_m H≈0.20 W/D≈1.1, ratio/HDRI/bg 랜덤 유지).
- 설정/라벨/머티리얼 변화 없음 확인.

### 풀 실행 커맨드 (메인이 실행)
```
bash scripts/data_prep/blender/run_dataset_v4.sh \
  --n_train 4000 --n_val 1000 \
  --out_dir data/pallet/training_data_v4_split \
  --seed 7000 --per_folder 200 --batch_size 200 --overlay_every 100
```
- 주의: 기존 파일럿이 `training_data_v4/{train,val}`(flat)에 있어 충돌 회피 위해 out_dir을 **새 디렉토리**(`training_data_v4_split`) 권장. 기존 v4에 그대로 쓰면 train_batch_*/val_batch_*가 train/,val/과 공존(겹치진 않음).
- 폴더 수: train 20개(train_batch_000..019) + val 5개(val_batch_000..004) = 25폴더, 총 5000장.
- 시간: ~약 2~3s/frame(파일럿 기준) → 5000장 약 3~5시간(통과율/리젝션에 따라 변동). 200장마다 fresh Blender 재시작.
- 디스크: png 640x480 + json + stats. overlay/_crop는 폴더당 every100(=2장)만.

## gen_dataset_v4: 저장 구조를 test_palletobj_r3(flat) 레이아웃으로 전환 + 기존 폴더 후처리 (3d-expert)

### 배경
v4 생성 중단 상태(`data/pallet/training_data_v4_split/`: train_batch_000/001 완성 200쌍, batch_002 부분 49쌍). 기존 구조가 `<batch>/{images,json,overlay(sparse, overlay_NNNNNN.png),_crop,_stats}/`로 분리돼 DOPE 로더가 바로 못 씀. 목표=`test_palletobj_r3` 동일 flat 구조.

### 목표 구조 (r3)
```
<batch>/000000.png  000000.json  ...      ← png+json 폴더 루트 colocated
<batch>/overlay/000000.png ...            ← overlay 전수, 파일명=frame index (overlay_ prefix 제거)
<out_root>/logs/                           ← chunk stats + run log (데이터 폴더 밖)
```
폴더당 200장 유지: train_batch_000~019(4000) + val_batch_000~004(1000). frame index 폴더 내 000000부터.

### 스크립트 수정
- `scripts/data_prep/blender/gen_dataset_v4.py`:
  - `main()`: `img_dir=json_dir=split_dir`(루트 저장), `ov_dir=split_dir/overlay`, `_crop`/`_stats` 디렉토리 생성 제거. stats는 `<split_dir 부모>/logs`(--flat_out) 또는 `<out_root>/logs`.
  - overlay 파일명 `overlay_{frame}.png` → `{frame:06d}.png`.
  - `save_crop()` 함수 + 호출 삭제(_crop 제거).
  - chunk stats 파일명 `stats_{batch_tag}_chunk_{idx}.json`(공유 logs 충돌 방지).
  - `--overlay_every` default 50 → 1(전수).
- `scripts/data_prep/blender/run_dataset_v4.sh`:
  - `fill_folder`의 `sdir="${fdir}/images"` → `sdir="$fdir"` ⇒ **resume = 폴더 루트 png 카운트**. overlay는 subdir라 `[0-9]*.png` 글롭에 안 잡힘(안전).
  - 최종 summary 글롭 `*/images/[0-9]*.png` → `*/[0-9]*.png`.
  - `OVERLAY_EVERY` default 100 → 1.

### 후처리 스크립트 (신규)

  - 결과: train_batch_000/001 각각 root png=200 json=200 overlay=200, subdir=overlay만. train_batch_002 통째 삭제. logs/에 stats_train_batch_000_chunk_000000.json, stats_train_batch_001_chunk_000000.json 보존.

## 나무 스킨 결 방향 데크 정렬 (per-texture uv_rotation) (3d-expert)

### 목적
목재 나무 스킨 11종 중 일부가 결/판자 줄무늬가 세로(데크 슬랫과 90도 직교)라
"팔레트 같지 않다"는 사용자 지적. 결을 데크 판자 길이 방향과 정렬.

### 진단 (확인)
- 9 base 텍스처 grain 방향을 gradient anisotropy 로 검출
  (`np.diff` 가로/세로 평균, 큰 쪽이 seam = 판자 직교축).
- 데크 mesh UV 는 텍스처 V축(세로)을 슬랫 길이 방향에 매핑.
  → 텍스처 판자가 "가로"(HORIZONTAL grain)면 슬랫과 직교 = 잘못.
- gradient 검출과 사용자 지적 6종이 11/11 정확히 일치:
  HORIZ(틀어짐) = weathered_brown_planks, wood_planks, brown_planks_04,
  plank_flooring_03, dark_planks → variant weathered_brown/weathered_warm/
  pine_warm/rough_tan/cabin_light/dark_knot.
  VERT(정상) = worn_planks, brown_planks_03, wood_planks_grey, weathered_planks.

### 수정
- `scripts/data_prep/blender/randomizers.py` `_configure_textured_material`
  (L283~): variant `uv_rotation`(deg) 추가. Mapping 노드 vector_type=POINT,
  Rotation.Z=radians, (0.5,0.5) UV 중심 회전 위해 Location=c-R*c 보정.
  (Blender 5.1 은 `vector_type`; `mapping_type` 아님 — 1회 헛돌음)
- `scripts/data_prep/blender/blender_config.py` `_variant_entry`(L172~):
  uv_rotation 키 화이트리스트 통과 추가 (안하면 드롭됨).
- `config/synthetic/blender.yaml` wood 그룹 6 variant 에 `"uv_rotation": 90`
  (weathered_brown, weathered_warm, pine_warm, rough_tan, cabin_light, dark_knot).
- 캐시키 `(family,name,source)` 는 variant name 고유라 rotation 충돌 없음.

## 바닥 텍스처 항상 회색 버그 수정 (BG_industrial 아스팔트 occlusion)

### 증상
gen_dataset_v4 생성물에서 `floor_texture` 라벨(red_brick/tile_white/wood 등)과
무관하게 바닥이 항상 같은 회색 아스팔트로 보임.

### 근본 원인 (raycast로 확정 — 사용자 가설 CONFIRMED)
- `randomizers.randomize_background()`는 매 프레임 `set_render_visibility(BG_industrial, True)`로
  BG_industrial 하위 164개 전체를 `hide_render=False`로 재노출.
- BG_industrial(FBX) 자체에 grey 아스팔트 지면 = **20개 `Floor*_Asphalt_0` 메시**가 surface z≈0에 존재
  (ancestors: Floor.NNN -> RootNode.001 -> *.fbx -> BG_industrial).
- `randomize_floor`의 `_hide_floor_grating()`은 무관한 3개(`Base_fence*`,`Base_base_m_0`,
  `Base_marks_m_0`)만 hide + `_floor_grating_hidden` 캐시라 frame2부터 no-op.
- 결과: FloorRandPlane(z=-6mm)이 z≈0 아스팔트 20장에 완전 가려짐.
  카메라 ray 143개 중 plane=1(0.7%) vs Floor.016/017_Asphalt=93%.
  → 회색의 정체 = BG 아스팔트(plane 텍스처/UV 문제 아님).
- 메모리36의 `base_m 그레이팅` 함정과는 다른 메시. 현 파이프라인(synth_data_scene.blend +
  BG_industrial)에서 회색 지면은 `Floor*_Asphalt_0`.

### 수정 (file:line)
- `scripts/data_prep/blender/blender_config.py` ~L205: `FLOOR_BG_GROUND_HIDE = ("Floor",)` 추가.
- `scripts/data_prep/blender/randomizers.py`:
  - import에 `FLOOR_BG_GROUND_HIDE` 추가.
  - `_hide_bg_ground()` 신규 함수(캐시 X, 매 프레임 실행). FloorRandPlane 제외 후 `Floor*` prefix
    메시 전부 hide.
  - `randomize_floor()` 내 `_hide_floor_grating()` 직후 `_hide_bg_ground()` 호출.

### 검증
- raycast: 수정 후 FloorRandPlane 93.7%(134/143 rays), 아스팔트 0.
  (`_diag_floor_occlusion.py`, `_diag_floor2.py`)
- 비교 렌더 6종 → `data/pallet/_floor_fix_test/_sheet.png`:
  floor ROI RGB stddev R25/G24/B36 (회색평준화 0). red_brick R163>>G65/B70,
  tile_white 최명도 196, wood 웜브라운 174, dirt 131, asphalt/concrete 그레이군.
