## 2. ★완료 인지 문제 — 원인과 수정

사용자가 **두 번째로** 지적했다("자꾸 끝났는데 인식 못하는 거 문제").
1만 장이 11:21 에 끝났는데 내가 몰랐고, 진행률 질문을 받고서야 발견했다.

### 원인 — 내가 만든 것

긴 background bash 가 죽는 걸 피하려고 `Start-Process` 로 **분리 실행**했는데,
**분리하면 하네스 작업 목록에서 사라져 완료 알림도 끊긴다.**
디스코드는 사용자 폰으로만 가고 내가 아는 경로가 아니다.
한 문제를 피하려다 다른 문제를 만들고 알아채지 못했다.

```
300장 x3 · tri A/B   background bash + Monitor   -> 알림 받음  ✅
1만 장               분리 실행, Monitor 없음      -> 알림 없음  ❌
```

부차 문제: 드라이버가 디스코드 호출을 `>/dev/null 2>&1` 로 침묵시켜
발송 실패해도 흔적이 없었다.

### 수정

1. 규칙을 프로젝트 memory 에 기록 — `longrun-completion-notice.md`.
   **분리 실행 = persistent Monitor 짝지어 등록**.
2. 드라이버 템플릿에서 알림 침묵 제거 — 전송 결과를 상태파일에 남긴다.
3. 실제로 작동하는지 검증(분리 작업 -> 60초 뒤 ALLDONE -> Monitor 즉시 감지) [확인].

### ★검증 중에 더 근본적인 결함을 찾았다

첫 검증 시도가 실패했는데 **감시가 21분간 조용히 기다렸다.**
원인은 `Start-Process -ArgumentList '-c','명령'` 형태가 동작하지 않아 테스트가
시작조차 못 한 것(1만 장 드라이버는 **스크립트 파일 경로**를 넘겨서 정상이었다).

★진짜 문제는 **내 감시 루프가 성공 마커만 봤다**는 것이다.  작업이 시작조차
안 되면 아무 신호 없이 영원히 기다린다 — **침묵을 성공으로 오해하는 것**이
원래 문제의 본질인데, 고치려던 장치가 같은 결함을 갖고 있었다.

그래서 감시를 네 갈래로 바꿨다: ALLDONE / ABORT·FAILED /
**N초 내 STARTED 없음** / **예상 시간 크게 초과**.

### ★"화면크기 >1.0" 은 0-항목이 아니다 — 내 판정이 틀렸다

처음에 18건을 "★실패"로 판정했다.  가설은 "팔레트 크기 지터(+20%)가
`proj_size_feasible_upper` 의 `PALLET_W=1.1` 고정값을 넘겼다" 였는데
**실측으로 기각됐다** — 실제 치수로 예측한 화면크기는 0.887인데 기록값은 1.618이다.

진짜 원인: `projected_size_actual` 은 **투영된 cuboid 의 u 범위**를 그대로 재므로
화면 밖 코너가 있으면 과대 측정된다.  18건 **전부(100%)** 잘린 프레임이었다:

```
화면크기 1.618  ->  u 범위 -573.3 ~ 332.7   (폭 560)
화면크기 1.106  ->  u 범위  360.9 ~ 1157.3  (폭 720)
```

`v2_realize.py:4633` 에 이미 적혀 있다 —
*"it can OVER-read when corners fall off-screen or behind the camera (known limitation)"*.

300장에서 0건이던 것도 설명된다: 잘림이 33%인데 그중 u 범위가 크게 벗어나는
극단만 1.0을 넘어 0.18%다 — 300장 기대치가 0.5건이다.

★**8월 3일에는 이 값(279.69)이 진짜 결함을 잡았다.**  차이는 그때 **거리 0.82m**
라는 다른 증거가 함께 있었다는 점이다.  구분 규칙:

```
진짜 결함    화면크기 > 1 + 거리가 하한(1.5m) 미만
아티팩트     화면크기 > 1 + 거리 정상 + 잘림 있음
```
