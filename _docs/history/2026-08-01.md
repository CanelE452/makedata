### 1. 구현 — `--session-usable-cap` + wrapper

2,000장을 한 Blender process 로 돌리지 않기 위해 `run_v2_scene_logic.py` 의 usable
mode 에 `--session-usable-cap K` 를 추가했다. K 장 전달 후 **정상 저장하고 exit 0**
으로 멈추며(`complete=false`, `session_paused=true`), 다음 실행이 같은 proposal
stream 위치에서 재개된다. 기본값 None 이면 기존 동작과 완전히 동일하다.

resume 자체는 **이미 구현돼 있었다** [확인] — `_resume_state()` 가 records +
rejected 의 최대 `proposal_index + 1` 을 계산하고, `iter_proposals()` 가 seed 로부터
stream 을 재생하며 `proposal_index < resume_from` 은 렌더도 기록도 하지 않는다.
quota 는 accept 시점에만 advance 하므로 replay 해도 진행이 같다. 그래서 cap 은
"이번 세션에서 새로 전달한 수"를 세어 루프를 조기 종료하는 최소 변경으로 충분했다.

단 기존 코드는 `not complete` 이면 `UsableCompletionError` 를 raise 했다 — cap 으로
멈춘 경우를 그 앞에서 분기해 정상 종료시켰다.

wrapper `run_v2_pilot_2k_repro.py` 신규: registry 로만 scene 을 해석하고
(경로 하드코딩 금지), session 을 순차 호출하며 progress 를 매번 확인해
`usable_delivered` 가 증가하지 않으면 중단한다. 병렬 Blender 를 만들지 않는다.

테스트 `tests/test_v2_pilot_resume_reproducibility.py` 24개 (bpy-free, 렌더 없음):
chunked replay 가 uninterrupted 와 proposal_index·FrameSpec·Plan canonical JSON·
reject 순서까지 동일한지, slot->mode 매핑이 세션 경계에 무관한지, cap 검증,
pause 분기가 raise 앞에 있는지. **unit 778 -> 802, skip 0.**
