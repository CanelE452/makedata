# 2026-08-04 — keypoint 가시성 정정(자체가림) · G1 근본 수정 · 카메라 하한

> 2026-08-03 의 1만 장 생성 이후, 그 데이터에서 찾은 품질 문제를 고친 기록.
> 코드는 이 문서 작성 시점에 커밋된다(직전까지 미커밋이었음).

## 결론 한 줄

**`visible_kp_count` 가 틀려 있었다 — 중앙점을 세고 자체가림을 무시해 "9개 전부 보임"이
21.7% 나왔다(육면체 상한은 7).  같은 버그가 탐색기 G1 에도 있었고, 그것까지 고치니
거부율이 74% -> 64.5% 로 내려가면서 4점 미만 프레임이 사라졌다.**

---

## 1. ★visible_kp_count 정정 (라벨 정확성)

사용자 지적: "어떻게 9개가 다 보인다는거지? 자체가림이 있어서 9개는 절대 다 보일 수 없는데.
그리고 중앙에 있는 점은 포함시키지 마 — 총 8개여야 PnP 를 제대로 한다."

**둘 다 맞았다.**  `run_v2_scene_logic._visible_keypoint_metrics` 는

```
uv9 = 8코너 + centroid                     <- 중앙점을 셌다
visible = in_frame AND (occ 미측정 OR occ<0.5)  <- 자체가림은 측정조차 안 함
```

`occlusion_fraction` 은 **외부 물체**에 의한 가림만 재고, 팔레트 자신의 뒷면 코너는
"미측정(None)" 이라 **보이는 것으로 처리**됐다.

수정: centroid 제외 + 자체가림 반영.  실측 30장에서 최대 9 -> 6 (상한 7 이내).

## 2. 자체가림 계산 — `SP2.self_visible_corner_mask`

볼록 육면체에서 코너는 **인접 3면 중 하나라도 전면이면** 보인다.  한 시점에서 전면은
1~3개뿐이라 보이는 코너는 **4 / 6 / 7 개**다 — 8개는 기하학적으로 불가능하다.

★**코너 순서에 의존하지 않게 만들었다.**  이 파이프라인에는 canonical 순서
(`blender_math.canonical_corners_yup`: 0=FTR 1=FTL 2=FBL 3=FBR 4=RTR 5=RTL 6=RBL 7=RBR)와
**v4 순열**(`perm_v4`, 예: [1,5,6,2,0,4,7,3]) 두 가지가 함께 돈다.  면을 인덱스로
박아두면 한쪽에서 반드시 틀리므로, **한 코너의 최근접 3점 = 세 모서리 방향**이라는
성질로 축을 기하에서 유도한다(면대각·체대각은 항상 모서리보다 길다).
순열을 넣어도 결과가 같음을 테스트로 고정.

## 3. ★G1 근본 수정 — 같은 버그가 탐색기에도 있었다

`SP2.external_corner_gate_metrics` 의 G1 은 **이미 "코너 4개 이상"을 요구**하고 있었다.
그런데 계산이

```
v_vis = v_inframe - ext_occ        <- 자체가림 누락
```

이라 실제보다 코너를 많게 셌다.  그래서 **탐색기는 "G1 통과"라 판단하고 렌더까지 했는데
라벨에서는 4점 미만**이 나왔다 — 거부율 74%의 주원인.

`self_visible=` 인자를 추가해 in_frame 과 교집합을 잡는다(인자를 안 주면 기존 동작 유지).

**왜 이게 최선인가** — 검토했다가 버린 대안들:

```
사후 게이트로 거부      렌더 다 하고 버림 = 낭비.  74%가 그 상태였다
앙각을 40° 이상으로     ✗ 사용자가 원하는 저앙각 정면 뷰를 없앤다
center side 신설       새 개념 + 기존 판정과 상호작용 위험
                       (G1.5 에서 순서 변경이 context 를 전멸시킨 전례)
★ G1 계산 정정          제약이 이미 있다.  계산만 고치면 탐색기가
                       "코너를 살리는 배치"를 스스로 찾는다
```

★**사용자가 지적한 두 상황이 자동으로 처리된다**:
- **0° 정면 뷰**: 자체가림으로 앞면 4코너만 보임 -> V_vis=4 -> G1 통과 (평면 PnP 로 풀림)
- **중앙만 가림**: 코너는 가림값이 낮음 -> V_vis 유지 -> G1 통과 (어렵지만 풀리는 좋은 케이스)
- **옆에서 코너 먹음**: V_vis<4 -> G1 탈락 -> 탐색기가 다른 배치를 찾음 (렌더 전에 걸러짐)

별도의 "center" 목표가 필요 없다.

## 4. PnP 최소 게이트 + 카메라 최소거리

- `PNP_MIN_VISIBLE_KEYPOINTS = 4` — 4점 미만 거부.  **하한만** 건다(4점 근처의 어려운
  케이스는 남겨야 한다는 사용자 요구).
- `MIN_CAMERA_DISTANCE_M = 1.5` + `proj_size_feasible_upper()` — 상한만 있고 하한이 없어
  카메라가 팔레트 안까지 들어갔다(화면크기 최대 279.69, 거리 0.49m).
  샘플링에서 ratio 상한을 걸고 solve_placement 에 방어 검사도 대칭 추가.

## 5. 분포 재조정 (잠정)

```
ELEV_BIN_FRAC  [0.08,0.18,0.20,0.20,0.16,0.10,0.08]
            -> [0.05,0.10,0.15,0.24,0.22,0.15,0.09]
V_FRAC         [0.15,0.25,0.30,0.20,0.10]
            -> [0.04,0.20,0.30,0.28,0.18]     (V=4 를 15%->4%)
```

★앙각 값에는 원래 `잠정 — 평가셋 실측 후 재조정할 것, 여기서 측정하지 말 것` 규약
주석이 있다.  평가셋은 이 머신 범위 밖이라 **"잠정치 재조정"으로 명시**하고 이전 값을
주석에 남겼다.  평가셋 통계가 나오면 그 값으로 다시 맞춰야 한다.

## 6. Figure 2 에 (c) 패널 신설 — 가시비율 x visible_kp

면적 가시비율과 keypoint 가시성은 **다른 축**이다: 가운데를 가리면 면적은 크게 줄어도
코너는 살고, 모서리 하나만 가려도 면적 손실은 작은데 keypoint 는 줄어든다.
PnP 난이도를 결정하는 것은 keypoint 쪽이므로 이 교차표가 있어야 판단이 된다.
0~7 고정(PnP 불가 구간 0~3 이 비어 있어도 보이게), 제목에 "occluded-but-5+ kp",
"PnP-impossible <4", 상한 초과 건수를 표기.

## 8. ★내 폴백 코드가 불가능한 값을 만들었다

300장 중 1건이 `visible_kp_count=8` (상한 7 초과).  원인은 내가 넣은 폴백:
3D 정보(corners_v4 / cam_pos)가 없을 때 `[True]*8`(전부 자체보임)로 채웠다 —
**없는 값을 지어낸 것**.  `None`(측정불가)로 바꿔 PnP 게이트가 unknown 으로 걸러내게 했다.
Figure 쪽도 상한 초과 값을 조용히 버리지 않고 축 라벨에 건수를 노출하도록 방어.

## 9. 내가 틀렸다가 정정한 것

1. **"앙각을 40° 이상으로 밀자"** -> 사용자가 원하는 저앙각 정면 뷰를 없애는 방향이었다.
   clean-static 실측에서 0~10° 도 평균 4점이 나와 PnP 가능함이 확인됐다.
2. **"4점은 위험"** -> 4점이 동일 평면이어도 평면 PnP 로 풀린다.  문제는 4점 **미만**이다.
3. **폴백 `[True]*8`** -> 지어낸 값.  None 이 맞다.
4. **속도 저하 15.69 s/usable** -> 로그 ctime 기준이라 틀렸다.  샤드 elapsed 기준 5.33.
