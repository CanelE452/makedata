```
uv9 = 8코너 + centroid                     <- 중앙점을 셌다
visible = in_frame AND (occ 미측정 OR occ<0.5)  <- 자체가림은 측정조차 안 함
```

`occlusion_fraction` 은 **외부 물체**에 의한 가림만 재고, 팔레트 자신의 뒷면 코너는

## 2. 자체가림 계산 — `SP2.self_visible_corner_mask`

볼록 육면체에서 코너는 **인접 3면 중 하나라도 전면이면** 보인다.  한 시점에서 전면은
1~3개뿐이라 보이는 코너는 **4 / 6 / 7 개**다 — 8개는 기하학적으로 불가능하다.

★**코너 순서에 의존하지 않게 만들었다.**  이 파이프라인에는 canonical 순서
(`blender_math.canonical_corners_yup`: 0=FTR 1=FTL 2=FBL 3=FBR 4=RTR 5=RTL 6=RBL 7=RBR)와
**v4 순열**(`perm_v4`, 예: [1,5,6,2,0,4,7,3]) 두 가지가 함께 돈다.  면을 인덱스로
박아두면 한쪽에서 반드시 틀리므로, ~~**한 코너의 최근접 3점 = 세 모서리 방향**이라는
성질로 축을 기하에서 유도한다(면대각·체대각은 항상 모서리보다 길다)~~
순열을 넣어도 결과가 같음을 테스트로 고정.

> ★**이 방법은 틀렸다 (3부에서 정정).**  면대각이 나머지 한 모서리보다 짧을 수 있다
> — 팔레트(0.792 x 1.125 x 0.154)에서 면대각 0.807 < 모서리 1.125 이라 최근접 3점이
> (모서리, 모서리, **면대각**)이 되어 축이 깨졌다.  결과적으로 보이는 코너를 7개 대신
> 6개로 셌다.  현재는 **서로 직교하는 유일한 3개 조합**을 찾는

★**사용자가 지적한 두 상황이 자동으로 처리된다**:

  남은 균등 인자가 그대로 나눠져 **자기교정**된다 — 그래서 지금까지 증상이 없었다.
- 축별 배율은 균등 fit 으로 되돌릴 수 없다.  이전 프레임의 왜곡이 current_dims 에
  박힌 채 새 왜곡이 곱해져 **종횡비가 프레임마다 random walk** 한다.
- `_normalization_cache` 는 target_dims 로 키를 잡는데 크기 지터가 연속값이라
  거의 항상 miss -> 매 프레임 재계산 -> 매 프레임 누적.

수정: `pallet_geometry.authored_scale(obj)` — .blend 원본 scale 을 **최초 1회만**
캡처해 고정.  첫 호출이 `_select_and_place_pallet` 의 `obj.scale` 쓰기보다 앞이고,
프로세스 재시작 시 .blend 를 다시 읽으므로 청크 분할 실행에서도 같은 값이다.

★**기존 1만 장·300장은 영향 없다** — 균등 배율만 쓰던 구간이라 자기교정이 작동했다.

## 4. Q3 — 거리 분포.  "10m 최다"는 그림 읽기의 함정이었지만 요구는 타당했다

Figure 1(b)는 **결합밀도**다.  10m 근처가 밝은 건 프레임이 많아서가 아니라 그 거리에서
화면크기가 좁은 범위(0.05~0.1)에 뭉쳐 단위면적당 밀도가 높기 때문이다.  실제 최다는
**1.5~2m (21.0%)** 였고, 9~10m 에 두 번째 봉우리(12.7%)가 있는 **쌍봉**이었다.

### ★ratio 가중치만으로는 못 고친다 — 두 가지 이유

1. `PROJ_SIZE_FRAC` **quota 가 구간 점유율을 강제**한다.  거리 선호 가중치를 걸어도
   실현이 정확히 0.200×5 로 나왔다(20,000회 실측).
2. ratio->거리 변환이 **fx 에 의존**한다.  fx 를 70% 랜덤(300~700)으로 돌리므로:

```
ratio 구간    fx=300       fx=450       fx=615       fx=700
0.20~0.40    1.5~2.6 m    1.9~3.9 m    2.6~5.3 m    3.0~6.0 m
0.60~1.00    - 불가        - 불가        1.5~1.8 m    1.5~2.0 m
```
   bin 4 는 고fx 에서 통째로 1.5~2.0m 라 구간 내부를 어떻게 뽑아도 못 뺀다.

### 구현 — 규약 변경 + fx 조건부 선호

- `DIST_PREF_MEDIAN_M = 3.5`, `DIST_PREF_LOG_SIGMA = 0.75` (로그정규 목표).
- `proj_size_bin_distance_spans(fx, W)` — **그 프레임의 intrinsics 로** 각 ratio 구간이
  덮는 거리 구간을 계산.
- `distance_pref_weights(spans)` — 목표 분포가 그 구간에 싣는 질량.
- `_deficit_pick(..., weight=)` — quota deficit 에 곱하는 **soft steer**.  실현 가능한
  구간은 1e-9 하한을 남겨 deficit 이 살아 있게 하고, 전 구간이 quota 를 채운
  fallback 도 균등이 아니라 선호 가중으로 뽑는다(대량 생성 후반부가 전부 이 경로).
- 구간 **내부**도 목표 분포 역변환으로 샘플링.  ratio-uniform 이면 거리 쪽이 1/d^2 로
  쏠려 근거리에 다시 쌓인다.  `_lognorm_cdf/_lognorm_icdf/_erfinv`(Winitzki + Newton
  3회, 왕복오차 1e-15) 신설.
- ★`PROJ_SIZE_FRAC` `[0.20]*5` -> **`[0.18, 0.25, 0.40, 0.15, 0.02]`**.
  실제 sample_frame 20,000회로 목표 히스토그램에 맞춰 격자 탐색한 값이다.

### 규약을 깬 것에 대한 기록

원래 균등 0.20 은 "기하 등비 구간 × 균등 = 거리 log-uniform = scale-invariant
커버리지"라는 **의도된 규약**이었다(v2 규약 Phase C).  이걸 배치 거리대 집중과
맞바꿨다.  **대가: 화면크기 ">60%"(초근접) 구간 20% -> 2%.**  초근접은 사용자가
1만 장 감사에서 직접 "너무 가까이 있는 건 문제"라고 지적한 구간이고, 2% 면 1만 장에서

## 1. 무엇이 틀렸나

1부에서 나는 코너 순서 비의존을 위해 면을 기하에서 유도했고, 주석에
**"면대각·체대각은 항상 모서리보다 길다"** 고 적었다.  **이게 틀렸다.**
면대각은 자기를 이루는 두 모서리보다는 길지만 **나머지 한 모서리보다 길다는 보장이
없다.**

실측 반례 (Pallet_3, 폭 0.792 x 깊이 1.125 x 높이 0.154):

```
모서리   0.154 · 0.792 · 1.125
면대각   sqrt(0.792^2 + 0.154^2) = 0.807   <- 세 번째 모서리 1.125 보다 짧다
```

코너 0 에서의 실제 거리: `[0, 0.792, 0.807, 0.154, 1.125, 1.376, 1.384, 1.135]`
-> 최근접 3점 = `(0.154, 0.792, 0.807)` = **(모서리, 모서리, 면대각)**.
진짜 세 번째 모서리(1.125)는 **네 번째**로 밀렸다.

결과: 축 두 개의 내적이 **0.98** (거의 나란함) -> `len(face) != 4` 에 걸려 그 축의
면 두 개가 통째로 건너뛰어짐 -> 전면 판정에서 빠짐 -> **보이는 코너 7 -> 6**.

## 2. 왜 테스트가 못 잡았나

1부 테스트는 `1.1 x 1.1 x 0.15` 정사각 상자만 썼다.
`sqrt(1.1^2 + 0.15^2) = 1.110 > 1.1` — **아슬아슬하게 통과**했다.
순열 불변성 테스트도 같은 상자를 써서 같이 통과했다.
★**형상 지터(2부)로 W != D 가 되면서 반례가 상시화됐다.**

2. **정사각 상자로만 테스트** -> 1.110 > 1.1 로 아슬아슬 통과해 버그를 가렸다.
   회귀 테스트는 **반례 도형**으로 짜야 한다.
3. **"키포인트 위치에 팔레트가 없다"** -> 거짓 경보.  야간 + 작은 크기.
4. **60장으로 거부율 40.0% 라 보고** -> 300장에서 49.5%.  60장 추정이 낙관적이었다.

**explicit 탐색의 holdout 렌더 2회를 1회로 합쳐 벽시계 -17.7% (결과 완전 동일).
반면 "후보를 렌더 전에 싸게 거르기"는 이득 -0.6% 에 결과까지 바뀌어 폐기했다 —
탐색기가 예산을 다 쓰므로 싸게 버린 자리를 다른 후보가 채운다.**

## 3. ★채택 — tri-holdout (렌더 2회 -> 1회)

후보 1개마다 렌더를 두 번 했다:
  (1) 팔레트 마스크(후보가 가린 상태)   (2) 후보 자체 가시 마스크(only_white)

두 장은 **같은 깊이 버퍼의 다른 라벨**이라 한 장으로 합칠 수 있다:
팔레트=흰255 / 후보=회128 / 나머지=검0, `팔레트 = v>=192`, `후보 = 64<=v<192`.
가시성은 색이 아니라 깊이가 정하므로 **근사가 아니다**.

### 구현 중 발견한 두 가지

```
_mask_area 의 `>127`     회색(128)을 흰색으로 센다 -> tri_mask_split 신설
픽셀 필터(기본 1.5px)     흰/회 경계를 ~190 으로 섞어 임계(192)를 흔든다
                         -> 3단계일 때만 filter_size=0.  2단계(배포 마스크)는 불변
```

★두 번째는 제안 시점에 놓쳤던 것이다.  "값만 분리하면 된다"고 했는데 그냥은 안 됐다.

### A/B (seed 9001, 60장씩, 순차)

```
동일성   usable_delivered 60=60 · render_attempts 101=101 · proposals_drawn 134=134
         · render_rejects 41=41 · 프레임 60개 x 지표 13종에서 **다른 값 0건**
속도     holdout 렌더 5,392 -> 3,628 (-32.7%)
         explicit 시간   700s ->   463s (-33.8%)
         ★벽시계       1,370s -> 1,128s (-17.7%), 장당 22.83 -> 18.80s
         렌더/평가       2.48 ->  1.67
```

★예상(25%)보다 낮다.  2.0 이 1.0 이 된 게 아니라 2.48 -> 1.67 이다 —
합칠 수 없는 렌더(조건부 amodal, 다른 단계 holdout)가 0.67 남는다.

커밋 606739a.  **기본 OFF**, `--tri-holdout` 으로만 켠다.

## 4. ★폐기 — explicit prescreen (렌더 전 기하 차단)

후보 투영 상자가 팔레트 목표 상자와 안 겹치면 렌더를 건너뛰는 규칙.
사전 분석은 좋아 보였다:

```
v5set 후보 8,908건 기준
   score_callback 탈락 6,752건 중 겹침 0 -> 1,428건 (21.1%)
   수락 343건 중 겹침 0 ->     0건 (0.0%)   오탐 없음
```

### 실험 결과 — 반증

```
                  off      tri      tri+prescreen
벽시계           1,370s   1,128s     1,121s
   tri 대비         —        —       ★-0.6%   (노이즈 수준)
holdout 렌더     5,392    3,628      3,295
prescreen 차단       0        0        296건   ← 차단은 실제로 됐다
★coarse 평가     2,172    2,172      2,178   ← 오히려 +6
```

★**탐색기가 평가 예산을 다 쓴다.**  후보 하나를 렌더 없이 버리면 그 자리에 다른
후보가 채워지므로, 싼 거부가 늘어난 만큼 비싼 평가가 그대로 다시 온다.
총 렌더는 333회 줄었지만(≈72초분) 벽시계로는 7초만 나타났다.

### 게다가 결과가 달라졌다

```
off 대비 다른 값: mask_area_visible 6 · elev_actual 4 · f_total 4 ·
                  visible_kp_count 4 · V_vis 4 · explicit_occluder_visible_pixels 3
```

"보수적이라 좋은 후보를 못 버린다"는 맞았지만(수락 오탐 0),
**탐색 순서가 바뀌어 다른 해에 수렴**한다.  그 가능성을 분석에서 놓쳤다.

**판정: 이득 -0.6% vs 결과 변경 -> 채택 근거 없음.  코드 되돌림.**

남기지 않은 이유: (1) RECORD_RENDERED_KEYS 는 테스트가 고정하는 계약이라 안 쓰는
필드를 넣으면 안 된다 (2) explicit_score 에 죽은 분기가 남는다 (3) ★"기본 OFF 라
안전"이 사실이 아니었다 — 스코프 오류로 controlled 아닌 프레임까지 전량 실패시켰다.

## 5. ★이 실험이 남긴 일반 교훈

**개별 후보를 싸게 거르는 방향은 이 탐색기에서 통하지 않는다.**
예산 소진형 탐색이라 절감이 곧바로 다른 평가로 상쇄된다.
G1.6 기록의 *"후보를 더 잘 고르는 게 아니라 **후보 자체를 덜 만드는** 쪽"* 이
그래서 맞는 말이었다 — 그건 **후보 생성 규칙**을 바꾸는 일이고, 품질 영향이 커서
locked benchmark(1회 ≈ 66분) 없이 손대면 안 된다.

제안했던 "기하 검사를 렌더 앞으로" 는 **이미 구현돼 있었다** —
탐색 루프가 이미 `support -> collision -> camera_clearance -> score_callback(렌더)`
순이다.  제안 전에 코드를 확인하지 않은 항목이었다.

## 6. 내가 틀렸다가 정정한 것 (4부)

1. **"explicit_occluder_not_visible 이 렌더 후 버려진다"** -> 조기 종료가 이미 있었다.
   거부 337건 중 286건이 rendered=False.
