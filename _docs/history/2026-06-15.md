```
정상    frame00 =  0.433 ... frame08 = 0.751 (직사각 명확)
```
grazing/얇음 군집(<=0.381)과 정상 직사각(>=0.433) 사이 gap에 임계 0.40 설정.

## preview10: 카메라 elevation 제한 + FRONT facing-margin 게이트 (top-down 근본 배제)

### 목적
평평 팔레트 + 거의 수직 탑다운에서 4개 옆면 facing 이 near-symmetric → FRONT(0123)가
프레임마다 다른 옆면에 붙는 ill-posed 문제를 카메라 각도 차원에서 근본 차단.
사용자 확정: 완전 탑다운 배제, 항상 한 옆면이 명확히 카메라를 마주보는 비스듬 뷰만.

### 변경 파일
**`scripts/data_prep/blender/blender_math.py`**
- `compute_perm_v4(..., return_margin=False)` 인자 추가 (L138). facing 계산을 raw dot(거리비례)
  에서 **정규화 cos** (면 normal 단위 · cam→면중심 방향 단위)로 교체 → dimensionless,
  프레임 간 비교 가능. `return_margin=True` 시 `(perm, facing_margin)` 반환,
  margin = |facingA−facingB| ∈ [0,2]. top-down 에서 ~0, 명확한 비스듬 뷰에서 ~1.

**`scripts/data_prep/blender/gen_preview10.py`**
- `mathutils` import 추가.
- 상수: `ELEV_MIN_DEG=25.0`, `ELEV_MAX_DEG=65.0`, `CAM_DIST_RANGE=(1.6,4.5)`,
  `FACING_MARGIN_MIN=0.30` (L64~).
- `sample_camera_elev(geom)` 신규 (L80~): randomize_camera 대신 사용. elevation 정의 =
  팔레트 centroid 수평면 기준 앙각. az∈[0,2π) 균등, elev∈[25,65]°, dist∈[1.6,4.5]m 샘플 →
  cam = cen + dist·(cosElev·cosAz, cosElev·sinAz, sinElev). atan2(cam_z−cen_z, horiz)==elev
  (정확). look_at = centroid. Blender cam obj 도 to_track_quat('-Z','Y')로 정렬.
- main 루프: `randomize_camera` → `sample_camera_elev` 교체, elev/azim 반환받음.
- gate (d) 신규 FRONT 안정성: `facing_margin >= 0.30` 미달 시 reject(재샘플).
  기존 connector-cross 게이트는 (e)로 밀림.
- `compute_annotation_v4`가 facing_margin 반환(7-tuple), JSON 에 `facing_margin`,
  `camera_elevation_deg`, `camera_azimuth_deg` 기록.

## perm_v4 vs 기존 라벨 정합성 정량 감사 (3d-expert)

### 목적
새 camera-facing 동적 0123(compute_perm_v4)과 기존 train_batch object-frame 고정 라벨의 disagreement rate 확정. 대량생성 전 라벨 정의 충돌 차단.

### (a) 기존 라벨 방식 = object-frame 고정 [확인]
- render_blender_data.py:62 get_pallet_geometry -> pallet_geometry.py:217 canonical_corners_yup(cbmin,cbmax).
- canonical_corners_yup (blender_math.py:85) 은 bbox min/max 만으로 corner 0~7 순서 결정 → 카메라 완전 무관.
- render_blender_data.py:70,122 가 이 순서를 projected_cuboid/cuboid 에 그대로 사용. compute_perm 호출 전혀 없음.
- 결론: 기존 라벨 = identity (입력 corner i 의 라벨 ID = i, object-frame 고정).

### (b) disagreement rate (감사 스크립트: scripts/data_prep/blender/_audit_perm_disagreement.py)
- train_batch_* 전수 2000장 (48 batch, cam_pos 누락 0):
  FRONT 불일치 1059/2000 = 53.0%, PERM 불일치 1179/2000 = 59.0%.
- v11 실제 학습셋 train/ 4000장: FRONT 52.8%, PERM 58.4% (동일 결론).
- 카메라 elevation 버킷: low(<15) FRONT49.5%, mid(15-35) 54.6%, high(35-60) 55.5% — 전 시점 균일하게 ~50%+.
- 1%(무시) / 10%(전면충돌) 기준 대비 5배 초과 → 전면 충돌.

### (c) 좌표 규약·부호 일관성 [확인]
- train_batch/train/preview10 모두 world Z-up (top_z>bot_z=0 접지, cam world 좌표).
- compute_perm_v4 는 world-frame z=height 만 사용(blender_math.py:176). OpenCV/USD cam-frame z 부호 미사용.
- → v3 폐기 원인(cam-frame z 부호 USD z<0 vs OpenCV z>0 뒤집힘) 은 v4 에 재발 불가. 부호 함정 없음.

### (d) front_cos>=0.40 게이트 시점 영향
- front_cos 분포(2000): min-0.361 p10-0.095 med0.445 p90 0.893 max1.0.
- front_cos<0.40 = 45.7%, <0.0 = 17.6%. 게이트가 기존 분포의 절반 가까이 컷 → forklift 저각도 비스듬 뷰 대거 손실 우려.
- 대안: 게이트를 "라벨 모호(grazing) 프레임 드롭"으로만 쓰고, 저각도 자체는 유지. 또는 front_facing_cos 를 라벨 신뢰도 플래그로 저장하고 학습 시 loss weight/샘플링에 반영(드롭 대신 down-weight). preview10 JSON 은 이미 front_facing_cos 필드 보유 → 플래그 방식 즉시 가능.

### (e) 학습 모델
- weights/pallet_v11: data/pallet/training_data/train(4000) 으로 fine-tune. 라벨에 keypoint_convention/perm_v4 필드 없음 = object-frame 고정으로 학습됨.
- pallet_category(pretrain), 2023/2024 DOPE 체크포인트 존재. paper_base / mixed_v8 / convert_to_camera_facing_v4.py 는 이 저장소에 부재(grep/glob 확인) — 사용자 인용 전제는 다른 맥락.

### 결론 (2 시나리오)
- S1 (새 데이터도 object-frame 고정으로 통일): compute_perm_v4 미적용, gen_preview10 의 v4 재배정 제거. 비용=거의 0(코드 1곳). v11 과 정합, 즉시 대량생성 가능. 단 카메라 동적 라벨의 (의도했던) 장점 포기.

## 탑뷰(high-elevation) 0123 게이트 stress test

### 목적
새 0123 태그(compute_perm_v4 normal-facing FRONT + front_cos grazing 게이트)가 거의 수직 탑다운을 포함한
다양한 카메라 elevation에서 제대로 동작하는지 데이터로 실증. 질문: "탑뷰에서도 잘 되나?"

### 방법
- 신규 스크립트 `scripts/data_prep/blender/gen_topview_test.py` (gen_preview10.py 복제+수정, preview10 미변경).
  - elevation을 20~88°로 확장(거의 수직 포함). front_cos>=0.40, facing_margin>=0.60 게이트는 유지.
  - 모든 candidate(retry 포함)를 reject reason × elevation 버킷으로 집계(preview10은 마지막 reason만 출력해 통계 불가).
  - N=24, Blender 5.1 headless + synth_data_scene.blend, Cycles 24spp. out=`data/pallet/_test_topview/`.
- candidates=1186 평가 → 24장 통과(약 10분).

- 통과 24장: 전부 conn_x=0(연결변 X-cross 없음), front_near=true(FRONT=카메라근접면).

### 결론
- (a) 모호한 거의-수직 탑뷰(>=60°)는 front_cos 게이트가 100% 자동 배제 → ill-posed 탑뷰가 학습셋에 안 들어옴(의도된 동작).
- (b) 게이트 통과시킨 라벨은 전부 정확(conn_x=0, FRONT=cam-facing, 육안 정상).
- 즉 "탑뷰에서 잘 되나?" → 통과시키는 것은 정확하고, 진짜 수직 탑뷰는 자동 제외된다. yes(안전하게 동작).
- 진짜 수직 탑뷰 데이터를 원하면 별도 convention(top-face 기준 yaw-only) 필요 — 현재 side-face FRONT 정의로는 ill-posed라 배제가 정답.
